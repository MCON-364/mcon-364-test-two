What actually went wrong?

The most important thing to understand: many submissions used the correct API names, but the code did not yet follow the correct execution pattern.

🧩

Correct tool, wrong operation boundary

A ConcurrentHashMap makes individual operations safe, but it does not automatically make a sequence like get-check-put atomic. 

stock.get(item);
check quantity;
stock.put(item, newValue);
⏳

Future was treated like a result

A Future is not the result itself. It is a handle to work that may complete later. 

Future<String> future =
    pool.submit(callable);

String result = future.get();
🧪

Tests were not used early enough

Concurrency code is difficult to reason about by inspection alone. Compilation and small tests catch many issues before submission.

  • Run after each TODO
  • Test simple cases first
  • Then test concurrent behavior
Workshop rule: When reviewing concurrent code, do not start by asking, “Which class did I use?” Start by asking, “What can happen at the same time?”

Part 1: Interactive Code Review

We will review an anonymized versions of a common dispatch() mistake. The goal is not to shame the mistake. The goal is to learn how to read concurrent code.

The assignment code 

/*
 *   Hand each task off to the pool. The work each thread does is:
 *     (a) upper-case the string
 *     (b) record the result by calling recordResult()
 *     (c) return the result
 *   Give back a handle to each piece of work so the caller can retrieve
 *   the results later. Do not wait for the results here.
 */
public List<Future<String>> dispatch(List<String> tasks) {
    // TODO 3
    return null; //placeholder
}

The intended behavior

String task
→
submit to pool
→
worker uppercases
→
Future result
The key pattern: each task should be handed to the pool, the worker should uppercase the string, the worker should record the result, and the caller should receive a Future.
Broken Version A — uppercasing before submission 
public List<Future<String>> dispatch(List<String> tasks) {

    return tasks.stream()
        .map(String::toUpperCase)
        .map(upper -> pool.submit(() -> {
            recordResult(upper);
            return upper;
        }))
        .toList();
}
What you should ask:
  • Where does the uppercasing happen?
  • Does the worker thread do the transformation?
  • What work is actually submitted to the pool?
  • Does this match the method specification?
Note: This code may appear to work for small examples because the final strings are uppercase. But it violates the intended concurrency design: the expensive or meaningful work should happen inside the submitted task.
Broken Version B — get() too early 
public List<String> dispatchAndCollect(List<String> tasks)
        throws Exception {

    List<String> results = new ArrayList<>();

    for (String task : tasks) {
        Future<String> future = pool.submit(() -> task.toUpperCase());
        results.add(future.get());
    }

    return results;
}
What you should ask:
  • What happens immediately after each submit?
  • Does the loop submit all tasks first?
  • How much concurrency do we actually get?
Problem: calling get() immediately blocks the loop. The next task is not submitted until the current one finishes.
Broken Version C — shared state updated without the intended method 
public List<Future<String>> dispatch(List<String> tasks) {

    return tasks.stream()
        .map(task -> pool.submit(() -> {
            String result = task.toUpperCase();

            results.add(result);
            completedCount++;

            return result;
        }))
        .toList();
}
What you should ask:
  • What shared state is being updated?
  • Can another thread interrupt between results.add() and completedCount++?
  • Why did the problem require recordResult()?
Problem: the list and counter must stay in sync. If two updates belong together, they must be protected together.
Corrected dispatch() pattern 
public List<Future<String>> dispatch(List<String> tasks) {

    return tasks.stream()
        .map(task ->
            pool.submit(() -> {
                String result = task.toUpperCase();
                recordResult(result);
                return result;
            })
        )
        .toList();

    public void recordResult(String result) {       // TODO 4 — owns the lock
        lock.lock();
        try {
            results.add(result);                    // both fields updated atomically
            completedCount++;
        } finally {
            lock.unlock();                          // always released
        }
    }

}
Why this works:
  • The task is submitted to the pool.
  • The worker thread performs the uppercase operation.
  • The worker records the result.
  • The caller receives a Future<String>.
  • The method does not wait here.

Part 2: Live Coding — Future / Callable Pattern

This is the pattern we want to burn into memory: submit all available work first, then collect results.

The mental model

Callable
work that returns
→
submit()
starts later/asap
→
Future
handle to result
→
get()
waits if needed
Say this out loud: submit() returns quickly. get() blocks. This is the pattern.

Step 1 — Sequential version

List<Integer> squares = numbers.stream()
    .map(n -> n * n)
    .toList();

This is simple and correct, but all work happens on the current thread.

Step 2 — Submit work to a pool

ExecutorService pool =
    Executors.newFixedThreadPool(4);

List<Future<Integer>> futures =
    numbers.stream()
        .map(n -> pool.submit(() -> n * n))
        .toList();

Now every number becomes a task. The result is not an integer yet. The result is a Future<Integer>.

Step 3 — Collect results later

List<Integer> results = new ArrayList<>();

for (Future<Integer> future : futures) {
    results.add(future.get());
}

This is where we wait for completed work and turn futures into actual results.

Step 4 — Shut down the pool

pool.shutdown();

if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
    pool.shutdownNow();
}

Executor services are resources. When we are done submitting work, we must shut them down.

Wrong pattern

for (Integer n : numbers) {
    Future<Integer> f =
        pool.submit(() -> n * n);

    results.add(f.get());
}

This submits one task, waits for it, then submits the next task. It destroys most of the concurrency.

Correct pattern

List<Future<Integer>> futures =
    numbers.stream()
        .map(n -> pool.submit(() -> n * n))
        .toList();

for (Future<Integer> f : futures) {
    results.add(f.get());
}

This submits all tasks first. Then it waits for results.

Demo Code: FuturePatternDemo.java

Use this small example before returning to the assignment problem. The goal is to isolate the pattern from the larger codebase. 

package edu.touro.mcon364.concurrency.remediation.demo;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.*;

public class FuturePatternDemo {

    public static void main(String[] args)
            throws ExecutionException, InterruptedException {

        ExecutorService pool = Executors.newFixedThreadPool(4);

        List<Integer> numbers = List.of(1, 2, 3, 4, 5, 6);

        List<Future<Integer>> futures = numbers.stream()
                .map(n -> pool.submit(() -> {
                    Thread.sleep(1000);
                    return n * n;
                }))
                .toList();

        System.out.println("All tasks submitted.");

        List<Integer> results = new ArrayList<>();

        for (Future<Integer> future : futures) {
            results.add(future.get());
        }

        System.out.println(results);

        pool.shutdown();
    }
}

Part 3: compute() and merge() Deep Dive

The most important idea: ConcurrentHashMap makes individual map operations safe, but not a multi-step check-then-update sequence.

The problem


            public boolean removeStock(String item, int qty) {
            // TODO: validate qty > 0
            if (qty <= 0){
            throw new IllegalArgumentException("Number of units to remove should be > 0") ;
            }
            Integer currentValue = stock.get(item);
            Integer newValue = stock.compute(item, (key, value) -> {
            return value >= qty? value -= qty: value;
            });
            return currentValue == newValue? false: true;

            // TODO: atomically check-and-decrement.
            //       If current stock >= qty, subtract qty.
            //       Otherwise, leave stock unchanged.
            //       Return true if stock was depleted, false if unchanged
            //       Hint: your chosen Map has a compute() method that lets you
            //             read and write in one atomic step.

            }

Solution 

public boolean removeStock(String item, int qty) {
    // validate qty > 0
    if (qty <= 0) {
        throw new IllegalArgumentException("Number of units to remove should be > 0");
    }
    Integer currentValue = stock.get(item);
    Integer newValue = stock.compute(item, (key, value) -> {
        return value >= qty ? value - qty : value;
    });
    return !currentValue.equals(newValue);
}

Unsafe check-then-act

Integer current = stock.get(item);

if (current == null || current < qty) {
    return false;
}

stock.put(item, current - qty);
return true;
Problem: another thread can change the map between get() and put().

Atomic compute()

stock.compute(item, (key, current) -> {

    if (current == null || current < qty) {
        return current;
    }

    return current - qty;
});
Why this works: the read, decision, and update happen as one atomic map operation for that key.

The signature

compute(K key, BiFunction<K, V, V> remappingFunction)
Part Meaning
K key The key whose value we want to update atomically.
BiFunction<K, V, V> A function that receives the key and current value, then returns the new value.
Return a new value The map entry is replaced with that value.
Return null The map entry is removed.
Return true or false Wrong idea. The lambda returns the new map value, not whether the operation succeeded.
Example 1 — Increment if exists 
stock.compute(item, (key, current) -> {

    if (current == null) {
        return null;
    }

    return current + amount;
});
This only changes existing items. If the item is missing, it remains missing.
Example 2 — Remove if condition is met 
stock.compute(item, (key, current) -> {

    if (current == null) {
        return null;
    }

    if (current == 0) {
        return null;
    }

    return current;
});
Returning null from the lambda removes the map entry.
Example 3 — Conditional update with success tracking 
AtomicBoolean removed = new AtomicBoolean(false);

stock.compute(item, (key, current) -> {

    if (current == null || current < qty) {
        return current;
    }

    removed.set(true);
    return current - qty;
});

return removed.get();
The map update is atomic, and the boolean records whether the update happened.

Why check-then-act fails: timeline

This is the race condition that compute() prevents.

Time Thread A Thread B Stock value
1 get("keyboard") → 5 5
2 get("keyboard") → 5 5
3 checks: 5 >= 4, allowed 5
4 checks: 5 >= 4, allowed 5
5 put("keyboard", 1) 1
6 put("keyboard", 1) 1
Bug: Both removals succeeded even though the inventory only had enough stock for one of them.

Part 4b: generateReport — Understanding the Data Hierarchy

Many students panicked when they saw List<List<Transaction>>. This section breaks down exactly what that type means, why it exists, and how to walk through it step by step.

Step 1 — Read the type from the outside in

TypeWhat one element represents
Transaction A single sale / payment: an id and an amount.
List<Transaction> One batch — a group of transactions that arrived together (e.g., one day's data).
List<List<Transaction>> Many batches. The outer list is just a collection of those day-sized groups.
Mental picture: Think of it as a box of envelopes. Each envelope (List<Transaction>) holds a stack of receipts (Transaction). The box (List<List<Transaction>>) holds all the envelopes. You process one envelope at a time, independently — perfect for concurrency.

Step 2 — Concrete example

batches (List<List<Transaction>>)
 │
 ├── batch 0  (List<Transaction>) ── [ T("t1",100), T("t2",200), T("t3", 50) ]
 ├── batch 1  (List<Transaction>) ── [ T("t4",300), T("t5", 75) ]
 └── batch 2  (List<Transaction>) ── [ T("t6", 25) ]

Each batch is submitted to the thread pool as one independent Callable. The pool runs them concurrently. Each callable returns one BatchStats.

Step 3 — Full implementation, line by line

public ReportSummary generateReport(List<List<Transaction>> batches, int workers)
        throws InterruptedException, ExecutionException {

    // ① Guard-rails
    if (batches == null || batches.isEmpty())
        throw new IllegalArgumentException("No transactions were provided");
    if (workers <= 0)
        throw new IllegalArgumentException("workers must be > 0");

    // ② Create the pool — workers controls the parallelism level
    ExecutorService pool = Executors.newFixedThreadPool(workers);
    List<Future<BatchStats>> futures = new ArrayList<>();

    // ③ Submit ONE task per batch — do NOT block here yet
    //    batches.get(i) is a List<Transaction> — one envelope
    for (List<Transaction> batch : batches) {
        futures.add(pool.submit(() -> {          // Callable<BatchStats>

            // IntSummaryStatistics gives sum, count, max, min in one pass
            IntSummaryStatistics stats =
                batch.stream()
                     .mapToInt(Transaction::amount)
                     .summaryStatistics();

            numberOfBatchesProcessed.incrementAndGet();  // thread-safe counter

            return new BatchStats(
                stats.getSum(),
                stats.getCount(),
                stats.getMax(),
                stats.getMin()
            );
        }));
    }
    // All tasks are now QUEUED — the pool is running them concurrently.
    // We haven't called future.get() yet, so we haven't blocked anyone.

    // ④ Now collect — future.get() blocks until that one task finishes
    long totalAmount = 0, totalCount = 0;
    int  globalMax   = Integer.MIN_VALUE;
    int  globalMin   = Integer.MAX_VALUE;

    for (Future<BatchStats> future : futures) {
        BatchStats bs = future.get();            // waits for THIS batch
        totalAmount += bs.totalAmount();
        totalCount  += bs.transactionCount();
        globalMax    = Math.max(globalMax, bs.maxTransactionAmount());
        globalMin    = Math.min(globalMin, bs.minTransactionAmount());
    }

    // ⑤ Release thread-pool resources
    pool.shutdown();

    // ⑥ Build and return the combined summary
    return new ReportSummary(
        totalAmount, totalCount,
        globalMax,   globalMin,
        numberOfBatchesProcessed.get()
    );
}

Why Future<BatchStats>, not Future<List<BatchStats>>?

Each task handles one batch and returns one BatchStats object. The outer List<Future<>> in your code plays the role of "one result slot per batch" — you don't need another nested list inside the Future.

Common mistake: submitting the entire List<List<Transaction>> as a single task. That would run everything sequentially inside one callable and defeat concurrency.

Why submit before collecting?

If you called future.get() right after each submit(), you would process batches one at a time — same as a plain loop. The trick is: submit all, then collect all. 

// ✅ CORRECT — submit all first
for (batch : batches)  futures.add(pool.submit(...));
for (f : futures)      result = f.get();   // NOW block

// ❌ WRONG — blocks immediately, no concurrency
for (batch : batches) {
    Future f = pool.submit(...);
    result = f.get();   // blocks before next submit
}

IntSummaryStatistics — do everything in one stream pass

IntSummaryStatistics stats =
    batch.stream()
         .mapToInt(Transaction::amount)
         .summaryStatistics();

stats.getSum();    // total amount for this batch
stats.getCount();  // number of transactions
stats.getMax();    // largest amount
stats.getMin();    // smallest amount
Why use this? One stream pass, four values. No need for four separate reduce operations.

Alternative: stream over batches instead of a for-loop

Instead of a for loop to submit tasks, you can use batches.stream().map(...) to produce the list of futures, and a second .stream().map(Future::get) to collect results. The logic is identical — only the shape of the code changes. 

// ③ Submit — stream over the outer list, one submit per batch
List<Future<BatchStats>> futures =
    batches.stream()
           .map(batch -> pool.submit(() -> {          // inner lambda = Callable<BatchStats>

               IntSummaryStatistics stats =
                   batch.stream()                      // <-- stream INSIDE the stream
                        .mapToInt(Transaction::amount)
                        .summaryStatistics();

               numberOfBatchesProcessed.incrementAndGet();

               return new BatchStats(
                   stats.getSum(),
                   stats.getCount(),
                   stats.getMax(),
                   stats.getMin()
               );
           }))
           .toList();   // ALL tasks are now queued; nothing has blocked yet

// ④ Collect — stream over futures, block on each .get()
List<BatchStats> results =
    futures.stream()
           .map(f -> {
               try { return f.get(); }
               catch (InterruptedException | ExecutionException e) {
                   throw new RuntimeException(e);   // wrap checked exceptions
               }
           })
           .toList();

// ⑤ Combine BatchStats into a single ReportSummary
long totalAmount = results.stream().mapToLong(BatchStats::totalAmount).sum();
long totalCount  = results.stream().mapToLong(BatchStats::transactionCount).sum();
int  globalMax   = results.stream().mapToInt(BatchStats::maxTransactionAmount).max().orElse(Integer.MIN_VALUE);
int  globalMin   = results.stream().mapToInt(BatchStats::minTransactionAmount).min().orElse(Integer.MAX_VALUE);

pool.shutdown();

return new ReportSummary(totalAmount, totalCount, globalMax, globalMin,
                         numberOfBatchesProcessed.get());
Key insight — two nested levels of streaming:
  • The outer .stream().map(batch -> pool.submit(...)) iterates over the envelopes (batches) and hands each one to the pool.
  • The inner batch.stream().mapToInt(...) runs inside the Callable, on a worker thread, summing the receipts inside one envelope.
  • .toList() on the outer stream materializes the list before any .get() is called — this is what guarantees all tasks are submitted before we start waiting.
Why the try/catch inside the lambda? Future::get throws checked exceptions (InterruptedException, ExecutionException). Stream lambdas cannot propagate checked exceptions, so you must either wrap them in a RuntimeException or extract a helper method.

for-loop style

for (List<Transaction> batch : batches)
    futures.add(pool.submit(...));

for (Future<BatchStats> f : futures)
    combine(f.get());

Easier to read for beginners; checked exceptions don't need wrapping.

stream style

List<Future<BatchStats>> futures =
    batches.stream()
           .map(batch -> pool.submit(...))
           .toList();

futures.stream()
       .map(f -> { try { return f.get(); } ... })
       .toList();

More functional; pairs naturally with further stream operations on results.

Concurrency Debugging Checklist

Use this checklist before submitting any concurrent Java code.

🔒

Shared state

  • What data can multiple threads touch?
  • Is it mutable?
  • Are related updates protected together?
🧮

Atomicity

  • Am I doing get-check-put?
  • Should this be compute()?
  • Should this be merge()?
📦

Futures

  • Did I save returned Futures?
  • Did I collect results with get()?
  • Did I avoid calling get() too early?
⚙️

Executor lifecycle

  • Did I call shutdown()?
  • Should I use awaitTermination()?
  • What happens if a task throws?
🧪

Testing

  • Does it compile?
  • Does the simple case pass?
  • Does the concurrent case pass?
📖

Specification reading

  • What should this method return?
  • Should this method wait?
  • Who owns the result collection?
